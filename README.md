# Toss

**Send it where you need it.** Toss is a private inbox for a person's iPhone, iPad, and Mac. It sends text, links, images, and files to a paired device, keeps the result available to act on later, and chooses delivery automatically: an app-authenticated, encrypted nearby transfer when possible; otherwise an end-to-end encrypted transfer through the user's private iCloud database. Files are limited to 20 MB.

This repository is an **engineering release candidate**, not a provisioned App Store build. Both app schemes compile and the core tests pass. Worldwide delivery, push delivery, App Group/Keychain sharing, and physical-device pairing still require the Apple Developer setup and manual verification below. No simulator or unit test can establish that an app has no security flaws.

## Project

`Toss.xcodeproj` is the existing iOS/iPadOS and macOS project; `project.yml` is its XcodeGen source. `Packages/TossCore` owns identity, pairing, encrypted persistence, direct transport, CloudKit mailbox, and the send/receive state machine. `Apps` contains the native interfaces; `Extensions` contains the iOS and macOS share extensions. There are no third-party packages, analytics, clipboard monitoring, or external AI services.

The app and its share extension share an AES-GCM-encrypted App Group state file and encrypted blob files, guarded by a cross-process lock. Extensions queue sends, confirm that opening Toss sends the item, and offer Done; the containing app handles delivery on its next active/scheduled pass. Encryption and identity keys live in a shared Keychain access group with `WhenUnlockedThisDeviceOnly` accessibility. Existing app-private keys are copied into the shared access group by the containing app on upgrade; the extension waits for the containing app to perform that migration. History search and content classification happen locally.

## Delivery behavior

1. The user picks a trusted device. Toss saves one logical `TransferItem` with a stable UUID in encrypted local storage and returns to the UI promptly.
2. If a nearby session is connected, Toss sends an authenticated AES-GCM envelope directly. If it has no authenticated receipt after five seconds, it can also upload the same logical transfer remotely. The receiver's replay ledger prevents duplicate Inbox items.
3. When direct delivery is unavailable, Toss encrypts the item locally and uploads the envelope as a `CKAsset` in the **private** CloudKit database. Upload means **Waiting for device**, not **Delivered**.
4. The receiving app fetches zone changes at launch, when active, on a best-effort push wakeup, and periodically while running. It accepts only a known sender public key, verifies the envelope and content, writes the item durably, and then uploads an encrypted receipt. Manual-approval devices acknowledge only after acceptance or decline.
5. The sending app marks **Delivered** only after verifying the receiver's authenticated receipt. A declined item is shown as failed. Receipts and retries are persisted across app restarts.

Cloud records use a custom `TossTransfers` zone. `EncryptedTransfer` and `EncryptedReceipt` records have fixed UUID-based record names, an encrypted `envelope` asset, and only routing fingerprints plus an expiry hint in ordinary fields. Titles, filenames, text, URLs, content types, and file bytes are inside the encrypted payload. CloudKit notifications are treated as change hints; the durable server change token controls incremental fetching. If a token expires, Toss refetches from the beginning. CloudKit does see account/container usage, ciphertext size, routing fingerprints, and record timing. The same iCloud account must be signed in on both devices for the private-database route; nearby sending can work without iCloud.

Encrypted payloads are removed after the receiver durably stores the item and uploads a receipt. The sender removes the receipt after processing it. For an undelivered transfer, the sender attempts to remove the payload 30 days after upload on its next run. **CloudKit provides no server-enforced TTL here:** if neither device runs again, an undelivered ciphertext asset can remain longer. Local History retention is separately configurable (Forever, 30 days, 90 days); replay IDs remain after visible history is deleted.

## Required Apple Developer setup

1. Open `Toss.xcodeproj` and assign one Apple development team to the two apps and two share extensions. Register the bundle IDs in `project.yml` or replace them consistently.
2. Register App Group `group.com.ethansoh.toss`. Enable it for each app and its corresponding share extension. Enable Keychain Sharing with the same team-prefixed `com.ethansoh.toss.shared` group on all four targets. Confirm the resolved `TossKeychainAccessGroup` Info.plist value matches the signed entitlement on each target.
3. Register CloudKit container `iCloud.com.ethansoh.toss` and enable iCloud/CloudKit for the two application targets. The extensions only queue into the protected App Group and use no CloudKit or nearby-network entitlement. Generate provisioning profiles with App Group and Keychain access for all four targets, plus iCloud and APNs for the applications as applicable. The iOS app declares `remote-notification` background mode; verify the capability is present in the signed app.
4. On a development-signed device, create a transfer and receipt to initialize the development CloudKit schema. In CloudKit Console, review the `EncryptedTransfer` and `EncryptedReceipt` types (`sender`, `recipient`, `expiresAt`, `envelope`), then deploy the schema to production **before** a release build. Validate both development and production environments with the intended signing profiles.
5. Use the same iCloud account on the paired devices, with CloudKit available. Pair using the existing QR flow while devices are nearby. Remote delivery uses the public keys established by pairing; an unknown device cannot become trusted merely by seeing CloudKit records or nearby discovery.

The project is generated by `xcodegen generate` after `project.yml` changes. Xcode 27 was used for the latest build. Example compilation checks:

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test --package-path Packages/TossCore
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Toss.xcodeproj -scheme Toss-iOS -configuration Debug -destination 'generic/platform=iOS Simulator' CODE_SIGN_IDENTITY='-' CODE_SIGNING_ALLOWED=YES build
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Toss.xcodeproj -scheme Toss-macOS -configuration Debug -destination 'generic/platform=macOS' CODE_SIGNING_ALLOWED=NO build
```

Ad hoc simulator signing strips the protected entitlements in this workspace. It verifies compilation but **cannot** verify App Group storage, shared Keychain, CloudKit, APNs, or real cross-device delivery. A simulator run may show a storage/signing error by design. Do not weaken the Keychain or storage checks to make an unsigned simulator appear functional.

## Security and privacy

Each installation generates a Curve25519 key-agreement private key in Keychain. The SHA-256 fingerprint of its public key is its app-owned device ID; no hardware identifier is used. QR pairing includes that public key and a random one-time secret valid for five minutes. The joining device prompts the user to confirm the target name and compare a 12-hex-digit public-key verification code shown on both devices before it sends a pairing hello. The joining device then proves knowledge of the QR secret with HMAC; the offering device consumes the offer after a successful join; the encrypted acknowledgement proves the offering device owns the QR public key. A displayed QR is a short-lived credential and should be treated as private.

Every transfer and receipt uses a fresh HKDF salt and AES-GCM key derived from the paired devices' Curve25519 shared secret. The version, envelope ID, sender ID, and receiver ID are authenticated as associated data. The payload binds the transfer UUID, item metadata, and file content. Both CloudKit records and nearby discovery labels are untrusted. A receiver validates sender trust, intended recipient, ciphertext integrity, item metadata, file type, size, and replay ID before showing content. Files have sanitized names and are stored under generated UUID paths; received content is never executed. URL actions use checked schemes and require a user tap. Notification text is generic by default; content previews are opt-in.

Forgetting a device removes its public key and prevents new authenticated incoming transfers or receipts from it. Previously delivered local content remains until deleted. Toss attempts to delete any pending encrypted payload for that device immediately and keeps a durable deletion request if offline; forgetting cannot revoke a remote device's copy of content it already decrypted. Static long-term agreement keys do not provide forward secrecy for ciphertext previously captured by an attacker who later steals a device private key. Key compromise requires re-pairing after secure key replacement; automatic rotation is not implemented.

See [toss-threat-model.md](toss-threat-model.md) for repository-grounded trust boundaries, attack paths, and residual risks.

## Manual release verification

- On provisioned iPhone/iPad/Mac devices: pair both directions, compare identity fingerprints, test an expired/reused QR, forget a device, and ensure old peers are refused.
- Send text, URL, image, PDF, and a near-20 MB file over nearby, cellular/different Wi-Fi, and with the recipient offline. Confirm one Inbox item and a sender status of **Waiting for device** until an authenticated receipt arrives.
- Disable iCloud and the network separately; confirm nearby still works without iCloud, remote sends queue locally, and retry resumes after connectivity returns. Sign into a different iCloud account and confirm the same-account limitation is communicated.
- Delay/drop push notifications; launch or foreground Toss and confirm missed changes are fetched. Test app termination and restart at each step: before upload, after upload, after local receipt persistence, and before sender receipt processing.
- Check share extensions from Safari, Photos, Files, and Finder. Confirm the queue confirmation and that queued sends finish when the containing app resumes. Test notifications with previews off/on, manual approval and decline, retention cleanup, and old-key or malformed-record rejection.
- Exercise VoiceOver, Dynamic Type, light/dark mode, reduced motion, oldest supported devices, shortcut conflicts, and memory/network usage at the 20 MB boundary.

The primary remaining release blockers are real provisioning and CloudKit schema deployment, multi-device worldwide transfer testing, extension handoff testing, APNs behavior testing, and an independent security review. iOS may delay or omit background pushes; launching or foregrounding Toss performs a sync. A share extension can queue securely and dismiss quickly, but iOS does not guarantee that its containing app will be launched solely because the extension queued a request. A nearby session is application-authenticated by its encrypted transfer and receipt, but the underlying Multipeer Connectivity session uses an unverified discovery name; if a peer spoofs one and withholds a receipt, the five-second fallback uses CloudKit when available. The nearby API is isolated for a future Network.framework migration.

## App Store preparation and privacy

Debug and Release configurations compile for both application schemes and both embedded extensions. Icons, display names, permission strings, macOS App Sandbox network/user-selected-file/Calendar access, iOS remote-notification mode, App Group, Keychain, and CloudKit entitlement declarations are present. Each executable bundle includes a `PrivacyInfo.xcprivacy` declaring app-only UserDefaults use and access to timestamps of Toss-owned temporary/container files; no tracking domains are declared. Review the final signed archive's entitlement and privacy report in Xcode before submission. A public privacy-policy URL, support contact, screenshots, age rating, and App Store Connect metadata still need to be supplied by the account owner.

For App Store Privacy answers, the implementation stores content and history locally and sends only encrypted transfer envelopes plus routing fingerprints, size/timing metadata, and acknowledgements to the user's **private** CloudKit database. It does not integrate analytics, ads, tracking, or a developer-operated content server. The app owner should verify whether Apple classifies this private CloudKit handling or any later support workflow as collected data for the final app/version, and keep the privacy manifest and App Store answers consistent. Do not claim that iCloud sees no information: it can observe account/container usage and traffic metadata even though Toss encrypts the item contents before upload. Apple requires accurate [App Privacy responses and an iOS privacy-policy URL](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy); its [required-reason API guidance](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype) documents the manifest categories and reasons used here.

### App Store Export Compliance

Toss uses Apple CryptoKit's Curve25519 key agreement, HKDF-SHA256, HMAC-SHA256, AES-GCM, and SHA-256 for pairing, transfer/receipt authentication, end-to-end encryption, and local storage encryption. It also relies on Apple's Keychain, Multipeer Connectivity encryption, and CloudKit transport. No custom cipher is implemented. The account owner must answer App Store Connect's encryption/export questions for the intended distribution regions and supply any requested documentation. `ITSAppUsesNonExemptEncryption` is intentionally **not** hardcoded until that determination is made. Apple's [export-compliance overview](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance) and [Info.plist key guidance](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption) describe the process; this README is technical inventory, not legal advice.

### Troubleshooting

- **Toss can't start:** inspect the signed App Group and Keychain Sharing entitlements on the app and extension. The resolved `TossKeychainAccessGroup` Info.plist value must match the team-prefixed entitlement. Open the containing app once before using an extension after upgrading from an older build.
- **Remote delivery unavailable:** confirm iCloud sign-in, the CloudKit container entitlement, the same container ID on both application targets, and production schema deployment. Nearby delivery remains independent of iCloud.
- **Waiting for device:** launch Toss on the recipient while online, then on the sender to fetch the encrypted receipt. Both must be signed into the same iCloud account. Background pushes are hints and can be delayed.
- **CloudKit quota or permission errors:** inspect the corresponding account/container in CloudKit Console and signing capabilities. Permanent errors appear as failed sends in History; transient failures remain queued for retry.
- **Share item remains queued:** open the containing app; iOS does not guarantee it will launch in the background just because a share extension wrote a request.
